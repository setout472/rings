# 复盘文章 · 骨架与草稿

> **目标**：一篇能被转发、被面试官读完的技术复盘。不是项目介绍，是「我踩了什么坑、怎么判断、边界在哪」。
> **长度**：3000–4000 字。**渠道**：掘金 / 少数派 / 公众号（技术向）；即刻、小红书发节选（产品向）。
> **用法**：正文草稿可以直接用；`✍️` 开头的是写作提示，定稿时删掉。

## 三、逐节草稿

### 00 · 开头

> ✍️ 提示：不要从「我做了个项目」开始，从一个具体画面开始。300 字以内必须出现第一个数字。

我想做一个工具：把一个人的相册变成一份他自己愿意看完的年度报告。

但我手上没有三千张能公开的照片——大多数人的相册里都有别人的脸。
所以我编了一份：一个在上海工作的人，2022 到 2024 年，3,736 张照片，11 次远行。

编的时候我给自己定了一条规矩：**数据可以假，规律不能假。**
于是我在 2022 年的春天留了一块空白——两个多月，一张照片都没有。

报告跑出来，它自己把那块空白算成了一行字：**最长的一次沉默，83 天。**

这句话我没有写进代码，是它自己算出来的。
那一刻我确定了一件事：这个项目难的部分不在把数据画成地图，
而在判断这 3,736 张里，哪些是真的。

---

### 01 · 我删掉了 9% 的照片

> ✍️ 提示：这一节建立「我不是随便删数据的人」，同时坦白第一次就删错了。要有心理描写。

第一版我加了一条看起来天经地义的规则：**相邻两张照片如果算出来的移动速度超过 900 km/h，
就判定 GPS 漂移，删掉。**

跑完，脚本告诉我：剔除 273 个漂移点。

> ✍️ 提示：**这个数字和仓库现在的状态对不上**——生成器修好之后，同样的规则只会删掉 5 个点。
> 发表时加一句括号注释，别让读者跑你的代码时发现对不上：
> 「（这是当时那版生成器的结果。修好之后，同一个规则只会删掉 5 个点——这也说明了一件事：
> 规则的输出完全取决于数据有多脏。）」

我盯着这个数字看了一会儿。273，占全部照片的 9%。如果这是一份真实用户的相册，
他丢掉的不只是 273 张照片，是 2022 年的一个春天。

于是我去看被删掉的那些点落在哪——**同一天，坐标在上海和三亚之间来回跳。**

问题不在过滤器，在我自己造的测试数据：我按「随机挑 130 天拍照」生成日常照片，
又单独生成了 12 次旅行，两者没有互斥。于是 1 月 3 日那天，这个人既在上海拍猫，也在三亚拍海。

> ✍️ 提示：这里要放一句能当金句的话。

**当清洗规则开始大量删除你的数据时，第一反应不该是调参数，而是回去看数据是不是自相矛盾。**
一个能在一天之内出现在两个城市的人，不存在。

---

### 02 · 958 km/h 的假阳性

> ✍️ 提示：这一节讲阈值。核心不是「我定了个数」，而是「我为什么定这个数、以及它排除了什么」。

修好数据之后，过滤器开始误伤另一种东西。

有两张照片相隔 14 秒、相距 4 公里——算出来 **958 km/h**，超音速，被判成漂移。
但这是我按连拍抖动造出来的正常照片。

问题在于：**间隔越短，速度对噪声越敏感。** 14 秒里坐标差 4 公里，在实际拍摄里可能只是
同一栋楼的两端、一次室内定位跳变，甚至是两台设备时钟没对齐。

所以判据里加了一个前提：

```python
if dist > 50 and dist / dt_h > 900:   # 位移不到 50km 的，速度再离谱也不判漂移
```

50 公里是个有依据的数：真实拍摄中，两张照片之间移动 50 公里以上，只可能是交通行为；
而交通行为的速度是物理有上限的（亚音速客机巡航约 850 km/h）。

> ✍️ 提示：一定要写「我以为我解决了」的转折，下一篇才有戏。

到这里我以为漂移问题解决了。**没有。**

---

### 03 · 10,079 公里的漏网之鱼

> ✍️ 提示：这一节是全篇最漂亮的一段——同一个 bug 的两种形态，第二种靠换判据才抓住。

改完阈值，报告里「2024 年最远的一次离家」显示：**10,079 公里**。

从上海出发，10,079 公里大约到南美洲。而我那年最远只到过新疆，四千公里出头。

这个点没被删，因为它落在一张相隔三天的照片旁边——三天走 10,079 公里，平均速度只有 140 km/h，
**完全合理**。速度判据天生看不见这种情况。

所以补了一条不依赖时间的判据：

```python
# 跟前后邻居都相距 3000km 以上的点，无论间隔多久，都不可能是真的
if d_prev > 3000 and d_next > 3000:
    bad.add(i)
```

这条判据的道理很朴素：**你不可能既离昨天那个地方三千公里，又离明天那个地方三千公里。**
它和时间无关，所以补上了速度判据的结构性盲区。

改完，那个数字从 10,079 变成 2,073。

> ✍️ 提示：一段话总结「两条判据各管一半」。

现在这条路上有两个判据：速度管「短间隔内的跳变」，邻居距离管「长间隔里的孤点」。
它们覆盖的是同一类错误的不同形态——这也是我后来写文档时反复强调的：
**一个异常判据永远只能覆盖异常的一半。**

### 04 · 三亚不在 UTC+7

> ✍️ 提示：这节最短，但「常识比公式重要」这个点很好用。

还有一个数字对不上：报告说我有 827 张「跨时区拍摄」的照片。

我那年只去过日本一次，加起来四百多张。827 明显多了。

原因是我用经度推算时区：`round(lon / 15)`。三亚的经度是 109.5°E，109.5 / 15 = 7.3，
四舍五入就是 **UTC+7**。

但中国全境只用东八区。地理经度和行政时区不是一回事。

修法很土：

```python
def tz_offset_hours(lon, lat):
    if 73 <= lon <= 135.5 and 18 <= lat <= 53.6:   # 中国大陆
        return 8
    return round(lon / 15)
```

改完，827 变成 275——只剩日本那趟，是对的。

> ✍️ 提示：这句要留着，它是整篇文章里最容易被引用的一句。

**公式告诉你 109.5°E 更接近 UTC+7，常识告诉你三亚人不用这个时间。代码里能写常识的地方，就别只写公式。**

### 05 · 换一种语言，怎么证明没换行为

> ✍️ 提示：这一节讲工程方法，别写成「我做了个大事」。重点是「怎么把感觉变成证据」。

工具跑通之后有个现实问题：它要装 Python、敲命令行。
我试着推荐给不写代码的朋友，基本卡在第一步。

于是决定把整个引擎搬到浏览器里：手写 EXIF 解析，聚类逻辑用 JS 重写一遍。
代价是——**同一套算法，现在有两个实现。**

两个实现最危险的地方不是写不出来，是「看起来一样」。你跑一遍，数字接近，就以为对了。
所以我做了对拍：同一份 3,736 张照片的数据，Python 跑一遍存成 JSON，
JS 跑一遍，逐字段比——照片数、去重数、漂移数、出行次数、每条行程的日期和照片数、每年的活跃天数……

**151 项。**

第一次跑就全过了。这不值得吹，因为 JS 版本来就是照着 Python 一行一行抄的。
真正抓到 bug 的是另一组测试：EXIF 解析器的测试图片。

我手工拼了一份大端（MM）的 TIFF 来做测试，结果解析全挂。查了半天发现是我拼错了——
ASCII 类型的值域固定占 4 字节，我只写了 3 字节，导致后面所有偏移整体错位 1 字节。

> ✍️ 提示：这里要坦白「测试也抓到了我自己的错」。

有意思的是，同一组测试还抓到了我另一处错误：南半球那条用例，我在期望值里写的是 `33 + 51/60`，
而夹具里用的是 `33.86`。**解析器是对的，我的期望值是错的。**

测试不偏袒任何一方。这就是它比「我觉得没问题」值钱的地方。

### 06 · 结尾

> ✍️ 提示：三条原则，每条一句话，不要展开成小作文。最后回到开头那个 83 天。

做完这个项目，我最想留下的不是那个地图，是三条判断：

**一、阈值要从数据里长出来。** 900 km/h 不是查来的，是「亚音速客机巡航 850」推出来的；
50 公里不是拍的，是「两张照片之间移动 50 公里只可能是交通行为」推出来的。
每个数字背后都要有一句人话，否则半年后你自己都不敢改它。

**二、每个删除动作都要能被审计。** 我保留了每张照片的时间来源（EXIF / 文件名 / 文件修改时间），
报告底部如实写出「3,679 张带定位 / 3,736 张总数 / 剔除 5 个漂移点」。
一个不告诉你哪里可能错的报告，不值得信。

**三、有两个实现，就要对拍。** 不是「跑起来差不多」，是逐字段比。
把「感觉一致」变成「151 项一致」，这件事只花了一个下午。

最后回到那份报告。它有 3,736 张照片、11 次出行、20 座城市、最远 4,181 公里。

但整个项目里我最想确认的，是代码有没有读出我埋下的那 83 天。它读出来了。

我编了一个人的三年，然后让代码把它读了一遍。它读对了——
这是这份假数据能给出的、最真的一次验证。

## 六、发出去之后怎么用

1. **简历**：项目条目下面加一行「技术复盘：<链接>」。面试官点进去看到 3000 字，
   基本不会再怀疑这个项目是不是抄的。
2. **面试**：被问「你遇到过什么坑」，直接讲 02 和 03 两节——一个假阳性、一个漏网，
   正好是一个完整的故事弧。
3. **追问预判**：
   - 「为什么不用现成的照片管理软件？」→ 它们不上传就做不了统计
   - 「准确率怎么算的？」→ 见 05 节，151 项对拍 + 8 项真值
   - 「数据是编的吧？」→ 是的，README 里写明了；但坑是真的，代码也是真的
4. **别做**：不要写「本项目使用了先进的 AI 技术」。这篇文章里没有一个 AI，
   全是判断力——而判断力才是面试官真正在找的东西。
