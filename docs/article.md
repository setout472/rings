# 我删掉了 9% 的照片：一次足迹可视化的数据清洗复盘

> 摘要：我做了一个把相册变成年度报告的小工具，最难的部分不是地图，是判断三千多张照片里哪些是真的。这篇文章记录四个数据陷阱，以及我怎么确认自己没把它们修错。
>
> 标签：数据清洗 / 可视化 / EXIF / 工程实践

---

我想做一个工具：把一个人的相册变成一份他自己愿意看完的年度报告。

但我手上没有三千张能公开的照片——大多数人的相册里都有别人的脸。所以我编了一份：一个在上海工作的人，2022 到 2024 年，3,736 张照片，11 次远行。

编的时候我给自己定了一条规矩：**数据可以假，规律不能假。** 于是我在 2022 年的春天留了一块空白——两个多月，一张照片都没有。

报告跑出来，它自己把那块空白算成了一行字：**最长的一次沉默，83 天。**

这句话我没有写进代码，是它自己算出来的。那一刻我确定了一件事：这个项目难的部分不在把数据画成地图，而在判断这 3,736 张里，哪些是真的。

---

## 一、我删掉了 9% 的照片

第一版我加了一条看起来天经地义的规则：**相邻两张照片如果算出来的移动速度超过 900 km/h，就判定 GPS 漂移，删掉。**

跑完，脚本告诉我：剔除 273 个漂移点。

273，占全部照片的 9%。如果这是一份真实用户的相册，他丢掉的不只是 273 张照片，是 2022 年的一个春天。

> （这是当时那版数据生成器的结果。修好之后，同一个规则只会删掉 5 个点——这也说明了一件事：清洗规则的输出，完全取决于数据有多脏。）

于是我去看被删掉的点落在哪——**同一天，坐标在上海和三亚之间来回跳。**

问题不在过滤器，在我自己造的数据。我按「随机挑 130 天拍照」生成日常照片，又单独生成了 12 次旅行，两者没有互斥。于是 1 月 3 日那天，这个人既在上海拍猫，也在三亚拍海。

一个能在一天之内出现在两个城市的人，不存在。

那天我学到的第一件事：**当清洗规则开始大量删除你的数据，第一反应不该是调参数，而是回去看数据是不是自相矛盾。**

---

## 二、958 km/h 的假阳性

修好数据之后，过滤器开始误伤另一种东西。

有两张照片相隔 14 秒、相距 4 公里——算出来 958 km/h，超音速，被判成漂移。但那是我按连拍抖动造的完全正常的照片。

问题在于：**间隔越短，速度对噪声越敏感。** 14 秒里坐标差 4 公里，在实际拍摄里可能只是同一栋楼的两端、一次室内定位跳变，或者两台设备时钟没对齐。

所以判据里加了一个前提：

```python
if dist > 50 and dist / dt_h > 900:
    # 位移不到 50km 的，速度再离谱也不判漂移
```

50 公里不是拍的。真实拍摄中，两张照片之间移动 50 公里以上，只可能是交通行为；而交通行为的速度有物理上限——亚音速客机巡航大约 850 km/h。

到这里我以为漂移问题解决了。并没有。

---

## 三、10,079 公里的漏网之鱼

改完阈值，报告里「2024 年最远的一次离家」显示：**10,079 公里。**

从上海出发，10,079 公里大约到南美洲。而我那年最远只到过新疆，四千公里出头。

这个点为什么没被删？因为它落在一张相隔三天的照片旁边——三天走 10,079 公里，平均速度只有 140 km/h，**完全合理**。

速度判据天生看不见这种情况。它只能描述「短时间内的跳变」，而这是一次「长时间里的漂移」。

所以补了一条不依赖时间的判据：

```python
# 跟前后邻居都相距 3000km 以上的点，无论间隔多久，都不可能是真的
if d_prev > 3000 and d_next > 3000:
    bad.add(i)
```

道理很朴素：**你不可能既离昨天那个地方三千公里，又离明天那个地方三千公里。**

改完，那个数字从 10,079 变成 2,073。

现在这条路上有两个判据：速度管短间隔内的跳变，邻居距离管长间隔里的孤点。它们覆盖的是同一类错误的不同形态。

**一个异常判据，永远只能覆盖异常的一半。**

---

## 四、三亚不在 UTC+7

还有一个数字对不上：报告说我有 827 张「跨时区拍摄」的照片。

我那年只去过日本一次，加起来四百多张。827 明显多了。

原因是我用经度推算时区：`round(lon / 15)`。三亚的经度是 109.5°E，109.5 / 15 = 7.3，四舍五入就是 UTC+7。

但中国全境只用东八区。地理经度和行政时区不是一回事。

修法很土：

```python
def tz_offset_hours(lon, lat):
    if 73 <= lon <= 135.5 and 18 <= lat <= 53.6:   # 中国大陆
        return 8
    return round(lon / 15)
```

改完，827 变成 275——只剩日本那趟，是对的。

**公式告诉你 109.5°E 更接近 UTC+7，常识告诉你三亚人不用这个时间。代码里能写常识的地方，就别只写公式。**

## 五、换一种语言，怎么证明没换行为

工具跑通之后有个现实问题：它要装 Python、敲命令行。我试着推荐给不写代码的朋友，基本卡在第一步。

于是决定把引擎搬到浏览器：手写 EXIF 解析，聚类逻辑用 JS 重写一遍。代价是——**同一套算法，现在有两个实现。**

两个实现最危险的地方不是写不出来，是「看起来一样」。你跑一遍，数字接近，就以为对了。

所以我做了对拍：同一份数据，Python 跑一遍存成 JSON，JS 跑一遍，逐字段比——照片数、去重数、漂移数、出行次数、每条行程的日期和照片数、每年的活跃天数。

**151 项。**

第一次跑就全过了。这不值得吹，因为 JS 版本来就是照着 Python 一行一行抄的。真正抓到 bug 的是另一组测试：EXIF 解析器的测试图片。

我手工拼了一份大端（MM）的 TIFF 用来测试，结果解析全挂。查了半天，是我自己拼错了——ASCII 类型的值域固定占 4 字节，我只写了 3 字节，导致后面所有偏移整体错位。

有意思的是，同一组测试还抓到了我另一处错误：南半球那条用例，我在期望值里写的是 `33 + 51/60`，而夹具里用的是 `33.86`。**解析器是对的，我的期望值是错的。**

**测试不偏袒任何一方。** 这就是它比「我觉得没问题」值钱的地方。

---

## 六、三条判断

做完这个项目，我最想留下的不是那张地图，是三条判断。

**一、阈值要从数据里长出来。** 900 km/h 是「亚音速客机巡航 850」推出来的，50 公里是「两张照片之间移动 50 公里只可能是交通行为」推出来的。每个数字背后都要有一句人话，否则半年后你自己都不敢改它。

**二、每个删除动作都要能被审计。** 我保留了每张照片的时间来源（EXIF / 文件名 / 文件修改时间），报告底部如实写出「3,679 张带定位 / 3,736 张总数 / 剔除 5 个漂移点」。一个不告诉你哪里可能错的报告，不值得信。

**三、有两个实现，就要对拍。** 不是「跑起来差不多」，是逐字段比。把「感觉一致」变成「151 项一致」，只花了一个下午。

---

最后回到那份报告。它有 3,736 张照片、11 次出行、20 座城市、最远 4,181 公里。

但整个项目里我最想确认的，是代码有没有读出我埋下的那 83 天。它读出来了。

我编了一个人的三年，然后让代码把它读了一遍。它读对了——这是这份假数据能给出的、最真的一次验证。
